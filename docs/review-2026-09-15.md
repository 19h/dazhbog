# Dazhbog startup and suggestion review

## Scope and evidence

Baseline: `3a76f27029fe7cf68064f8d50c986414b60952a6`. Implementation was integrated
with the user's intervening `4225d5d` commit. Existing `research/` and the original
`data/` were preserved. Subsequent source/document edits followed the file editing
tool constraint; no Python was used. Every completed group followed the requested explicit-path
`git add`, `red -m --staged --run`, `git push` sequence.

The tested copy is `/tmp/dazhbog-review-snapshot-20260915`, created using an APFS
clone after checking for open database handles. Its configuration is
`/tmp/dazhbog-review-benchmark.toml`; listeners are loopback ports 29667/29668 and
no upstreams are configured. Opening sled is writable even for inspection tools.

## Implemented behavior

- Exact per-tree cardinality and serialized-value bytes are updated in the same
  sled transaction as each counted mutation. Normal startup reads these counters
  instead of scanning records, latest entries and binary metadata.
- Existing stores open concurrently. Explicit offline preparation handles scans,
  legacy migration, context reconstruction and a new canonical search generation.
  The generation is published after completion and flush; older generations remain.
- Strict preparation fails on unresolvable keys. Explicit salvage preparation
  reports exclusions in `quarantine.jsonl` and preserves primary storage.
- Default suggestions use a coherent stored name/payload pair. Cross-version
  synthesis is experimental. Duplicate request keys retain output order and
  multiplicity without multiplying batch evidence; a key cannot supply its own
  second-pass anchor evidence.
- Canonical visibility is shared by preparation, browser detail and neighbors.
  Tombstones delimit live intervals. Cross-key ancestry cannot enter selected
  versions or history responses. Traversal is bounded at 4,096 records.
- Compound-symbol queries have indexed token positions. Search no longer rewrites
  documents during queries. Neighbor retrieval and reranking share generic-token
  exclusions, including corrected calling-convention/SIMD prefix handling.
- Upstream Lumina hits are shaped for requested metadata keys and report the
  resulting length. Raw upstream data is retained for caching.
- CRC-valid malformed record extents are rejected before slicing. Canonical and
  historical CRC algorithms share immutable compile-time tables.
- The server uses the library's module graph, drains connections on shutdown and
  flushes stores. Docker builds/copies the correct recovery target and excludes
  data, research and build products from its build context. CLI examples now use
  accepted dotted configuration syntax.

## Startup measurements

Host: Mac16,5, arm64, 128 GiB RAM, macOS 27.0 build 26A5425a. Native compiler:
`rustc 1.100.0-nightly (f248f4038 2026-09-05)`, locked release profile with fat LTO.
The original search manifest contained 15,018,336 live documents in 12 segments.

Salvage preparation completed in 1,069.36 s, indexing 14,598,322 documents and
quarantining 556 keys. Peak RSS was 27,048,394,752 B / 2^30 = 25.19 GiB. The active
generation is `search_index.prepared-1789498968346485000`. This run used per-key
delete/add insertion even though the new generation was empty; the implementation
now avoids those redundant deletion operations. The revised full-corpus peak has
not been remeasured. The original search count and new projection count differ
because the new projection applies current canonical visibility and name policy;
the difference is not the quarantine count.

The first diagnostic restart completed metrics at 1.692 s and the useful request
set at 3.055 s. A subsequent 20-run warm series before timeline-read reuse measured:

| Measurement | Median / s | p95 / s | Maximum / s |
|---|---:|---:|---:|
| Metrics readiness | 1.668 | 1.786 | 2.184 |
| Full useful request set | 2.104 | 2.218 | 2.631 |

Binary detail took approximately 0.42 s in that series; search took approximately
0.009 s and neighbors approximately 0.013 s. A repeated seed-observation read in
family timelines was removed subsequently. The final 20-run series also includes
streamed membership aggregation, heap-based function paging and concurrent binary
detail reads after facet preparation:

| Measurement | Median / s | p95 / s | Maximum / s |
|---|---:|---:|---:|
| Metrics readiness | 1.657 | 1.710 | 1.759 |
| Full useful request set | 2.038 | 2.087 | 2.139 |

All 20 runs completed the request set and shut down cleanly. These are uncontrolled
warm-cache measurements. The ≤2 s full-useful target remains unmet in this sample.
Context-store opening dominates readiness (approximately 1.64 s); binary detail
adds approximately 0.37 s after search. Removing application-level corpus scans
does not eliminate sled's own opening/recovery cost. No deployment latency
guarantee follows from this host-specific result. [A1, A2]

Cold-cache measurement is **unknown**: `/usr/sbin/purge` returned
`Operation not permitted`, and `sudo -n /usr/sbin/purge` required a password.
No cold series was run or inferred from warm measurements. The full-useful ≤2 s
cold-start acceptance criterion is therefore not established. [A1, A2]

The benchmark distinguishes first successful metrics response (`ready_s`) from
completion of search, function detail, neighbors, binary detail, alternate-RPC
pull and Lumina v3 hello (`useful_s`). It starts and stops only its own child,
checks ports before startup, closes request connections and verifies clean exit.
Polling interval is 0.010 s; scheduler delay adds uncertainty. Reported percentiles
use nearest rank and describe the observed sample, not a deployment guarantee.

## Complexity and durability boundaries

Let `R` be traversed records, `S` segment trees, `K` latest keys, `C` retrieved
candidates, `B` analyzed metadata bytes and `T` distinct batch tokens.

- Startup application statistics cost O(S) counter reads, independent of total
  record count. Sled recovery/snapshot parsing and Tantivy opening still depend
  on physical storage state; startup is not universally O(1).
- A counted mutation adds O(1) fixed-width counter arithmetic and transactional
  tree operations; sled's own indexing/storage costs remain.
- Canonical/history traversal uses O(min(R, 4096)) reads and visited addresses,
  plus record/name analysis. Candidate analysis additionally costs O(B).
- Preparation streams one projected document at a time plus the Tantivy writer's
  buffers; it does not retain all K documents in an application vector or enqueue
  a redundant deletion per key. This is not a bound on total process RSS.
  Its work includes K lookups, bounded per-key history and metadata analysis.
- Neighbor evaluation bounds C to 24..384; production retains its prior 24..96
  candidate budget. Reranking sorts O(C log C) results after analysis/context I/O.
- Batch anchor normalization sorts T accumulated token weights once and subtracts
  the target key's contribution without copying the full token map per key.
- Related/overlap aggregation streams membership/counts instead of repeatedly
  loading/sorting full binary metadata per association. Final metadata lookup is
  once per aggregate binary; the underlying scan remains proportional to observed
  memberships. Malformed count values retain the prior zero-count interpretation.
- For N seed keys and M related binaries, timeline seed-observation reads fall
  from N*M to N, using O(N) temporary counts (N ≤ 8192); target-observation reads
  and summation remain O(N*M). The per-key minimum-count semantics are unchanged.
- For N functions in a binary and P = min(N, offset + limit), page selection
  costs O(N log(P + 1) + P log(P + 1)) time and O(P) retained entries, rather
  than sorting/storing all N for a small first page. It still scans N entries
  for an exact valid-entry total. Huge offsets retain the original O(N) space
  bound. Zero-size pages retain no candidates.
- Binary detail prepares facets, then joins four independent reads on the
  blocking pool. This changes scheduling, not response fields; graph/timeline
  dependencies on facet preparation are preserved. HTTP concurrency is not a
  process-wide allocation or job-queue bound.

No transaction spans segments, latest, context and search. Graceful flush improves
shutdown behavior but is not proof of arbitrary power-loss atomicity. Preparation
cannot reconstruct observations absent from primary records and surviving context.
